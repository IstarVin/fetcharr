## Confirmed server bugs

### 1. [P1] Failed overwrite destroys original subtitles

- **Location:** `server/internal/process/place.go:40–58`, `:91–99`.
- **Trigger:** Overwrite an existing item with a subtitle of the same language,
  then fail the media placement, for example from an I/O error or an interrupted
  cross-filesystem copy.
- **Impact:** Subtitle placement has already replaced the original subtitle.
  Rollback deletes the replacement without restoring the original. The old
  media remains, but its original subtitle is lost.
- **Evidence:** A temporary overlay test pre-created an original subtitle,
  allowed subtitle replacement, injected media-placement failure, and asserted
  that the original remained. That assertion failed: the subtitle path no
  longer existed. The test did not modify application source.
- **Recommendation:** Stage replacement files, retain originals until the
  complete placement succeeds, and restore originals on failure. Cover both
  rename and cross-filesystem placement failures.

### 2. [P1] Delayed Cancel kills a new retry and leaves it stuck

- **Location:** `server/internal/runner/runner.go:261–275`, `:417–435`,
  `:458–470`; `worker.go:149–156`; `service/service.go:342–385`, `:432–442`.
- **Trigger:** Cancel a pending job. After `Stop` checks the cancelled status
  but before it acquires the runner lock, retry the job and let its new worker
  start. The delayed stop then targets the new worker registered under the
  same job ID.
- **Impact:** The new download is cancelled and its work directory deleted,
  while the database still reports `downloading`. No worker remains to finish
  it. Restart recovery or further manual intervention is required.
- **Evidence:** A temporary overlay inserted a scheduling barrier between the
  existing status check and lock acquisition. A test using real service Cancel,
  Retry and dispatcher operations reproduced `final status=downloading, active
  downloads=0, work directory removed`. The root reviewer reran it successfully.
  The shared settings read lock permits these actions to overlap.
- **Recommendation:** Associate lifecycle side effects with a specific execution
  generation, and reject stale stop requests. Add a deterministic overlapping
  Cancel/Retry regression test.

## Android state and notification bugs

### 3. [P1] Old-server action responses enter the new server's queue

- **Location:** `data/sync/JobActions.kt:88–137`;
  `data/sync/SyncManager.kt:104–107` beneath
  `android/app/src/main/kotlin/com/istarvin/fetcharr/`.
- **Trigger:** Start a pause/resume/retry/cancel request on server A, switch to
  server B before the response arrives, then let A's response complete.
- **Impact:** Sync clears A's queue on switching, but `JobActions` subsequently
  upserts A's response into B's store. Old jobs can appear in the new queue and
  influence background-service and completion-notification decisions.
- **Evidence:** Action helpers capture an API before suspension and mutate the
  shared store afterward without checking the current connection. The same
  omission affects conflict-refresh paths. A temporary Android regression test
  delayed A's response, switched configuration to B, cleared the old queue and
  added B's job. Releasing the response failed the isolation assertion: the
  store contained both B's job and A's old job, rather than only B's job.
- **Recommendation:** Capture a connection generation for requests and reject
  every store mutation when that generation has changed. Test delayed single,
  batch and conflict-refresh responses.

### 4. [P2] Notification catch-up can mix two servers

- **Location:** `notifications/ResultNotifier.kt:103–116`, `:132–144`;
  `notifications/ApiJobsGateway.kt:17–36`.
- **Trigger:** Switch servers while a notification catch-up request is pending.
- **Impact:** Results from A can be processed after switching to B. A subsequent
  batch lookup obtains the currently configured API, so it can query B with A's
  batch ID. Stale notifications or incorrect notification state can result.
- **Evidence:** Identity is checked before the suspending catch-up operations,
  with no corresponding check before processing their results. Batch lookups
  independently obtain the current API.
- **Recommendation:** Bind the catch-up, batch lookups, posting and persisted
  state to one captured connection generation; cancel or discard stale work.

### 5. [P2] A later completion prevents retrying a failed notification

- **Location:** `notifications/ResultNotifier.kt:98–116`, `:133`, `:165–168`.
- **Trigger:** Batch-summary lookup for completion T fails; a later live
  completion T+1 succeeds before reconnect.
- **Impact:** T+1 advances the global `lastSeen` timestamp past T. Subsequent
  catch-up requests exclude T, so the failed summary is never retried despite
  the documented recovery behavior.
- **Recommendation:** Persist pending failed notifications separately, or only
  advance a recovery cursor over a fully handled range. Test failed batch
  lookup followed by an unrelated successful live completion and reconnect.

### 6. [P2] Large notification queries silently return incomplete results

- **Location:** `notifications/ApiJobsGateway.kt:17–37`, `:47–51`;
  `server/internal/store/jobstore.go:339–361`;
  `server/internal/service/service.go:182–205`.
- **Trigger:** More than 2,000 finished jobs need catch-up, or one batch has more
  than 500 jobs. The server has no episode-count limit enforcing that boundary.
- **Impact:** Catch-up stops after ten pages and returns partial results as
  success. Because the server returns newest-created jobs first, processing
  those results can advance the timestamp past omitted older completions.
  Batch summaries also use only one page and can show incomplete counts.
- **Recommendation:** Represent incomplete pagination explicitly. Fully page
  batch results, and use ordered/keyset catch-up that can safely continue
  without moving the cursor past unprocessed results.

## Android task-recovery and design issues

### 7. [P2] Authentication recovery opens Settings behind the incoming sheet

- **Location:** `ui/incoming/IncomingSheet.kt:64–65`, `:92–95`;
  `ui/FetcharrAppUi.kt:191–194`.
- **Trigger:** Submit an incoming request with an invalid token and tap its
  Settings recovery action.
- **Impact:** Settings opens underneath the modal. A server URL is still saved,
  so the modal's hide condition remains false and blocks credential editing.
  Dismissing/cancelling the request is the available workaround.
- **Recommendation:** Suspend the incoming sheet during credential recovery,
  preserve its request, and restore it after leaving Settings.

### 8. [P2] Empty categories leave Add disabled without recovery guidance

- **Location:** `ui/add/AddViewModel.kt:51–58`, `:106–108`;
  `ui/add/AddScreen.kt:184–187`; `data/CategoryRepository.kt:46–55`.
- **Trigger:** A server is configured but its category cache is empty; the
  one-time refresh fails or the server has no categories yet.
- **Impact:** Add has no selected layout and cannot submit, with no category
  loading/error/empty explanation or retry action. A transient refresh failure
  does not retry within this view model. New servers with zero categories are
  a supported setup state.
- **Recommendation:** Model loading, failed and empty category states. Provide
  retry for failures and a route to configure destinations for an empty server.

### 9. [P2] Saving server settings consumes Back without a response

- **Location:** `ui/settings/ServerSettingsScreen.kt:77–82`, `:107`.
- **Trigger:** Save server settings while the network request is slow.
- **Impact:** System Back is intercepted and does nothing during saving; toolbar
  Back is also disabled. The user must wait for the request to finish or fail.
  The base client has a 30-second read timeout and no overall call timeout.
- **Recommendation:** Define safe leave/cancel behavior for pending saves and
  keep system navigation responsive, with clear messaging about save status.

### 10. [P2] Add submission failures can be outside the visible viewport

- **Location:** `ui/add/AddScreen.kt:122–135`, `:151–155`, `:261–269`.
- **Trigger:** Submit from the fixed footer while the scrollable form's end is
  below the viewport, particularly with several headers or subtitles.
- **Impact:** The error is appended at the form's end with no scroll, focus,
  snackbar or live-region announcement. The button re-enables without an
  immediately perceivable explanation, including for TalkBack users.
- **Recommendation:** Put an announced error summary near the submit action or
  move focus/scroll to the error while preserving the form.

### 11. [P2] Large expanded batches compose every row eagerly

- **Location:** `ui/queue/QueueScreen.kt:167–183`, `:456–467`;
  `ui/incoming/IncomingSheet.kt:188–205`.
- **Trigger:** Expand or receive a batch with many episodes.
- **Impact:** A whole queue batch occupies one lazy item, with an ordinary
  `Column` composing every expanded child. Incoming episode lists also eagerly
  render all episodes. This creates a scaling risk for large supported batches;
  actual frame-time impact was not measured in this pass.
- **Recommendation:** Flatten expanded jobs into keyed lazy rows and use a
  single appropriate lazy scroll container for long incoming episode lists.
